# Planted-gap curriculum: summary (2026-10-22)

The question: which kinds of gaps does GapFinder find? Gaps were planted on papers it already reproduces, and it
searched for them without the paper (`--hypotheses repomap`; the only model calls are the search's name matching, under $0.01 a batch). Built by `eval/planted/curriculum.py`
(design in its docstring); the per-task tables are generated by `curriculum.py report`:

- [c1, seed 2](planted_curriculum_c1_seed2.md): engine tag `planted-c1`, 14 gap tasks and 11 controls.
- [c1, seed 3](planted_curriculum_c1_seed3.md) and [c2, seed 3](planted_curriculum_c2_seed3.md): 16 fresh gap
  tasks, made after c2 was frozen, searched by both versions.
- [c1, seed 4](planted_curriculum_c1_seed4.md) and [c3, seed 4](planted_curriculum_c3_seed4.md): 13 fresh gap
  tasks and 11 controls, made after c3 was frozen, searched by both versions.
- [c3, seed 5](planted_curriculum_c3_seed5.md) and [c4, seed 5](planted_curriculum_c4_seed5.md): 14 fresh gap
  tasks and 9 controls, made after c4 was frozen, searched by both versions (c4 with the code proposer).
- [c3, seed 6](planted_curriculum_c3_seed6.md) and [c5, seed 6](planted_curriculum_c5_seed6.md): 16 fresh gap
  tasks and 9 controls, made after c5 was frozen, searched by both versions (c5 with the code proposer).
- [c5, seed 7](planted_curriculum_c5_seed7.md) and [c6, seed 7](planted_curriculum_c6_seed7.md): 27 fresh gap
  tasks and 14 controls, made after c6 was frozen; c5 as adopted against c6 with the code proposer.

These are development measurements. The builder knows every family, and the generator ran on six papers
(pygcn, FastGCN, Fair Clustering, SparseTSF, RippleNet, VGAE). They are not blind evidence.

## What GapFinder finds (c1)

Planted gap tasks, seeds 2 and 3 together:

| Family | Level 1 (>= 5 sd) | Level 2 (3-5 sd) |
|---|---|---|
| Scale or unit convention ("the paper's v is the code's 2 x v") | 4 of 4 | 2 of 3 |
| Setting (a flag or a constant at another value) | 0 of 9 | 2 of 9 |
| Code defect (an arithmetic or reduction edit) | 0 of 3 | 0 of 2 |
| Reporting rule, paper-era code, old package release | not planted | not planted |
| **All** | **4 of 16** | **4 of 14** |

- **Confidently wrong: 0 of 30 gap tasks and 0 of 11 controls.** Every miss carried an unconfident label
  ("Fits but unsupported", "Unexplained" or "Inconclusive"), and every control was reported as reproduced.
- **Scale conventions are found.** The scale probe names the knob and the factor and labels it a paper-artifact
  inconsistency.
- **Settings are mostly not found.** Of the 16 setting misses, 10 come close in at least one way. 6 name the
  planted knob at another value (`hidden1=160` for a planted 4), and 7 have it among the configurations GapFinder
  says the target can't tell apart.
  On pygcn the task gives one number (Cora accuracy only), so several settings fit it equally well. GapFinder says
  so, but the scorer counts it as missed.
- **Code defects are not found.** A code round was cut by the run budget in 19 of the 30 searches (section 7.1 of docs/CONTEXT_v11.md has every failure class). In 4 of the 6 level-1 misses on seed 2, a code round ran out of budget: the patch
  round was one run short of the planted constant (VGAE, twice), and the mutation round never ran (RippleNet,
  FastGCN).
- **Reporting rules, paper-era code and old package releases could not be tested here.** The rebuilt harnesses
  (`eval/planted/rebuild_harnesses.py`) offered these draws on five papers. None moved the target by 3 sd, so no
  such task was made (the rebuilt harnesses produced only controls). Their evidence is still the acceptance toys.
- **The gate was not passed.** Level 1 needs 70% of gap tasks correct; c1 got 25%. Levels 3-5 (two causes,
  adversarial causes outside every family) were not run.

## c2 against c1 on a fresh batch

c2 (`planted-c2`, ca4a5e2) adds `code_hold`. When the code has leads, the patch and mutation rounds' shares are
kept out of the settings exploration. A mutant found after an unsupported fit is reported as an alternative, not
as the answer.

| | c1 | c2 |
|---|---|---|
| Seed 3, level 1 | 3 of 9 | 6 of 9 |
| Seed 3, level 2 | 1 of 7 | 1 of 7 |
| Seed 3, code-defect tasks | 0 of 3 | 0 of 3 |
| Seed 3, confidently wrong | 0 | 0 |
| Dev suite (69 cause runs; c1 = run 5000, c2 = run 6000) | 52 | 48 |
| Dev suite, confidently wrong | 0 | 0 |

- **Seed 3:** c2 is better on 4 tasks and worse on 1 (sign test p = 0.38).
- **Dev suite:** c2 is better on 2 tasks and worse on 6 (p = 0.29).
- **Neither difference is significant, and the gains are not the intended ones.** Every seed-3 gain is a setting
  task; code defects stay at 0 of 3. One gain (pygcn, `lr=0.0025`) was a pick among tied configurations. The
  hold did let the mutation round run (VGAE: 22 mutants tested), but the planted site was not among them. Mutation
  sites are taken from the data flow of the known knobs and the metric code, and `gae/layers.py:30` is on neither.
- **Recommendation:** don't freeze c2 as the next version on this evidence. The next code-defect bottleneck is
  mutation-site coverage, and that fix would need its own fresh batch.

## c3 against c1 on a fresh batch (seed 4)

c3 (`planted-c3`, 96f43d9) is plan F1-F10 (docs/CONTEXT_v11.md 7.1). The main changes:
- mutation sites ranked on the metric's output slice;
- the code rounds' first tests run early, and a class scheduler shares the budget between settings and code;
- value intervals for the answer's knob;
- group screening of mutation sites;
- a "not identifiable" note.

Seed 4 adds DeepCrime's real-fault operators to the code and data families, and gives pygcn's tasks a two-point
paper sweep.

| | c1 | c3 |
|---|---|---|
| Level 1 (9 gap tasks) | 3 | 4 |
| Level 2 (4 gap tasks) | 1 | 2 |
| Scale or unit convention (6) | 3 | 4 |
| Setting (2) | 1 | 1 |
| Code defect (2) | 0 | 1 |
| Data: training data cut to a half or three quarters (DeepCrime TRD, 3) | 0 | 0 |
| Confidently wrong, gap tasks | 1 | 0 |
| Controls (11) | 11 correct | 11 correct |
| Dev suite (69 cause runs; c1 = run 5000, c3 = run 7000) | 52 | 48 |
| Dev suite, confidently wrong | 0 | 0 |

- **Seed 4:** c3 is better on 2 tasks and worse on none (sign test p = 0.5).
- **Dev suite:** c3 is better on 2 tasks and worse on 5 (p = 0.45), within the ±5 that replicates of identical
  code swing. Its largest drop, `dev-rl-schedule` (3 of 3 to 1 of 3), is a tie between two settings in the first
  pass. None of c3's new rounds ran there.
- **The first planted code defect found.** RippleNet's `np.mean(auc_list)` -> `np.sum(auc_list)` was found by
  c3's mutation round (labelled Fits but unsupported). c1 found nothing.
- **c1's one confidently wrong answer is gone.** On a pygcn weight-decay convention, c1 gave `0.00075` as a
  paper-artifact inconsistency. c3 gave the planted `0.001`.
- **c3 gave no confident label on any gap task. Its correct scale answers are all "Fits but unsupported".**
  - The scale probe's guard, added with F4, reports "0 of the 3 swept claims were off as run" on clear scale gaps.
    It judges "off as run" with the noise floor, the same mistake fixed in the mutation round's guard (96f43d9).
  - The "not identifiable" note also counts the answer plus a knob that does nothing as an alternative.
  - Both are defects for the next version.
- **Training data cut (DeepCrime TRD): 0 of 3.** GapFinder has no operator that removes training data. Each answer
  was a setting that moves the number alike, labelled Fits but unsupported, which is the right label for a cause
  outside its families.
- **pygcn is still missed with its paper sweep** (a learning-rate convention x0.01, and `epochs=100`). The planted
  knob is among the configurations c3 says the claims can't tell apart.
- **Reporting rules, paper-era code and package releases still produced only controls** on the five rebuilt
  harnesses.
- **The gate is not passed:** 6 of 13 gap tasks (46%) against 70%.

## c4 against c3 on a fresh batch (seed 5)

c4 (`planted-c4`, 268e52c) is plan G1-G8 (docs/CONTEXT_v11.md 7.1): the off-as-run guards on the runs' own spread,
passengers not counted as rivals, the scale probe on a log scale, a training-subset operator with stratified
mutant selection, and a code proposer (one Super call when nothing fits). Its answer before the proposer ran is
kept, so this one batch also scores c4 without it.

| | c3 | c4 | c4 without the proposer |
|---|---|---|---|
| Gap tasks (14) | 4 | 5 | 5 |
| Gap tasks without the training-data cuts (10) | 4 | 2 | 2 |
| Training-data cuts (4) | 0 | 3 | 3 |
| Confidently wrong | 0 | 0 | 0 |
| Correct with a confident label | 1 | 0 | 0 |
| Controls (9) | 9 correct | 9 correct | |
| In a credible set of at most 3 | 3 | 3 | |
| Dev suite, two replicates each (138 cause runs; c1 against c4) | 100 (c1) | 96 | |

- **c4's net +1 is not a gain.**
  - All 3 gains are training-data cuts. Two were drawn from GapFinder's own new operator: the generator draws code
    and data tasks from the engine's mutation operators, and it ran on c4's code. Those tasks test the operator on
    itself.
  - On the other 10 tasks c4 is worse: 2 against 4.
- **The two losses come from c4's own changes:**
  - **Stratified mutant selection.** The early code screen's first 6 mutants are now taken from each operator
    class in turn. Data and loop mutants displaced Fair Clustering's planted `0.5 -> 1.0`, which c3 ran among its
    first 6, and the mutation round then ran out of budget.
  - **The log-scale scale probe.** For RippleNet's epochs (paper's v = code's 0.5 x v), it picked a factor of 1/3.
    That maps the swept values to 3.33, 6.67 and 13.3 epochs, which can't be run. c3, reading the curve linearly,
    picked 0.5 and verified it.
- **G1 did not restore confident labels.** c3's one confident correct answer (VGAE's x0.01 learning rate) lost its
  label in c4: the scale probe's verification got 7 of its 10 runs before the budget ended, so one swept claim had
  none.
- **The code proposer was not really tested.** It made 6 calls and proposed 8 edits. 7 were refused as not parsing:
  the model writes statements (`X = X_org`) and pieces of multi-line expressions, and the grounding accepts one
  whole expression. The one edit that ran didn't fit. The model calls for the whole round cost $0.024.
- **Dev suite: no regression.** Fresh replicates of c1 and c4, run side by side, gave 48 and 50 of 69. Two
  replicates each give 100 and 96 of 138 (p = 0.39), with 0 confidently wrong.

## c5 against c3 on a fresh batch (seed 6)

c5 (`planted-c5`, deea98f) is c4 with plan H1-H4: valid scale factors for an integer knob, with the runner-up
verified; the first mutants in plain priority order; line-text edits for the code proposer; and the scale probe's
verification fitted to the budget.

The batch was made with H5:
- code and data tasks are drawn from the operators frozen at c1, never from the engine under test;
- the DeepCrime data cut keeps a spread 40% or 60% of the training data, not the engine's first half or three
  quarters.

| | c3 | c5 | c5 without the proposer |
|---|---|---|---|
| Gap tasks (16) | 5 | 7 | 7 |
| Confidently wrong | 0 | 0 | 0 |
| Correct with a confident label | 1 | 2 | |
| In a credible set of at most 3 | 2 | 5 | |
| Mean reciprocal rank | 0.30 | 0.40 | |
| Controls (9) | 9 correct | 9 correct | |
| Dev suite, two replicates each (138 cause runs; c1 against c5) | 100 (c1) | 99 | |

- **Per task, c5 is better on 2 and worse on none** (sign test p = 0.5). The gains:
  - a DeepCrime training-data cut on VGAE (a spread 60%), found by the engine's first-half operator at the cut's site:
    the class, not its expression;
  - FastGCN's epochs convention (x0.5), where c3 answered a learning rate.
- **Confidence returned where it is due.** Fair Clustering's x0.5 convention is a Paper-artifact inconsistency in
  c5; c3 gave Fits but unsupported (G1).
- **Dev suite:** c5's two replicates give 52 and 47 of 69, 99 of 138 against c1's 100 (p = 0.75). 0 confidently
  wrong, and all 114 abstentions correct.
- **The code proposer barely ran.** It runs only when nothing fits every claim, and here that happened twice. Of
  its 2 edits, 1 was grounded and didn't fit. The model calls for the round cost $0.012. It remains unmeasured.
- **What is still missed:**
  - 3 of the 4 training-data cuts: the engine's 1/2 and 3/4 don't match a spread 40% or 60% within noise on
    RippleNet and FastGCN, or 40% on VGAE;
  - a layer bias added (DeepCrime WAB): no operator does it;
  - 6 settings: ties on pygcn's single number, and literal split fractions off the grid (`test_ratio=0.05`,
    `test_percent=7.5`).
- **Fixed in the scorer, not the engine.** A planted reporting rule now counts as found when GapFinder lists it among
  the equally good readings of the runs, as a planted value counts inside the set of equally good values. On seed 6
  both versions answered "best validation epoch" with the planted "each metric's best epoch" listed as equally good,
  and the old check scored that confidently wrong. This is the first batch with a reporting task.
- **Infrastructure:** four pygcn searches failed at one moment on a Sandboxes operation error the searcher did not
  retry. They were resumed from their runs, and that error is now retried.

## c6 against c5 on a fresh batch (seed 7)

c6 (`planted-c6`, 4c7c679) is plan I (docs/CONTEXT_v11.md 6.1):
- split constants as leads, with their crossing screened;
- the code proposer on unsupported fits;
- a data-cut fraction from a log-scale secant;
- a structural-switch operator;
- planted gaps at least 1% of the value.

The batch was meant to be about 45 gap tasks. It came to 27: the 1% rule and families short of draws.

| | c5 (adopted) | c6 | c6 without the proposer |
|---|---|---|---|
| Gap tasks (27) | 10 | 7 | 7 |
| Confidently wrong | 0 | **2** | |
| Searches that crashed | 0 | 2 | |
| Correct with a confident label | 2 | 2 | |
| Controls (14) | 14 correct | 14 correct | |
| Dev suite, two replicates (138 cause runs) | 99 | 97 | |

By family (c5 / c6): setting 4/8 and 3/8, scale 3/9 and 3/9, data 2/5 and 1/5, code 0/4 and 0/4, reporting 1/1
and 0/1 (a crash).

- **Per task, c6 is better on 1 and worse on 4** (sign test p = 0.375). **c6 is not adopted; c5 stays.**
- **The two confidently wrong answers come from the scale probe trying more than one factor:**
  - RippleNet: the true x0.5 failed verification on noisy runs, and the runner-up x1/3 (added in c5, H1) then
    fit by chance;
  - pygcn: a training-data cut, answered as weight decay x0.01, a factor the curve can't judge that is run
    (added in c4, G4), which fit pygcn's flat response.
  - The confident label doesn't account for how many factors were tried, and c5 has the same logic.

  - the data-cut secant overflowed (0.5 raised to a huge power) when the cut barely moved the number.
- **The proposer added nothing** (7 with and without it).
- **The planned power was not reached.** 5 tasks differed, so a sign test could not have shown significance,
  whichever way they went.

## c7 against c5 on a fresh batch (seed 8): plan, written before the batch was made

c7 (`planted-c7`) is c5 with two changes, found by re-running earlier real papers on c5 for the showcase
(`demo/runs/real/`), where c5 did worse than earlier versions on VGAE and RippleNet:
- **A.** The minimal-set step cut a knob on one run of the subset. When the subset's repeats then neither close the
  gap nor stay within a band of the full set, each cut is decided again on repeats. On VGAE, the documented split
  pair (test 10%, validation 5%) fits, but test_percent alone fit on its one run and failed on three.
- **B.** One tie rule on every path that picks an answer. A tie the target can't break keeps the earlier
  candidate, unless only the later one has evidence. Otherwise the closer fit wins. On RippleNet, the path taken when
  the budget ran out picked lr=0.002 over the repo-declared lr=0.001 on the closer mean alone (0.693 +- 0.003 against
  0.688 +- 0.010).

Both rules predate c1. These real papers revealed them, so they are not evidence for c7.

Before the batch was made, the owner asked for every earlier real paper to end with a good result. So c7 also
carries the class-level fixes for the other failures found then (each diagnosed from its c5 run, each with a toy):
- **C.** A counterfactual whose configuration has no successful run is marked unchecked. It used to crash the
  search: MC Dropout, three times.
- **D.** The scale probe ignores a claim that a factor leaves where it is (0 under any multiplier); that claim
  had ruled out every factor. Also, the probe's held runs (plan H4) are kept from every stage before it. c5's
  hold counted the claims in the wrong list and was always 0. (GCN attack: x0.5 never scored; the probe ran with 1
  run of 200 left.)
- **E.** Static code leads on code the dry run executed rank first, before the cut. Ties sorted by file path had
  put a vendored copy (PatchTST) and detectors the run never used (BOND) in the slots.
- **F.** Runs held for the protocol tests, which ran last and got none, when an evaluation switch sits on
  executed code (PatchTST: the test loader's drop_last never ran).
- **G.** The values the paper states for the target's own dataset are tested together as one block (GAT:
  PubMed's lr and heads, each screened alone on one run).
- **H.** The paper-to-code contrast sees the executed source lines and states a true premise. A structural
  difference needs the paper's words verbatim and a line that ran. It is reported, never tested (pygcn: the
  prompt saw no code).

The harnesses of SDCN and BOND are rebuilt with the current builder, which records per-epoch values and
per-package pins. Their old harnesses predate both.

On the planted batch, A, B, D, E and F can act. G and H can't, because the tasks carry no paper; C fires only on
a failed run.

**The batch.** Seed 8, the size of seed 7: 4 tasks per case and level on the hand harnesses, 2 on the -h ones. It
is searched by c5 as adopted and by c7, both with the proposer off, so the arms differ only by A and B. The dev
suite is run twice on c7 (bases 12000 and 12100) against c5's 10000 and 10100.

**Power, stated in advance.** A scan of 563 recorded searches found A's situation in 4 of them (under 1%). B changes an
answer only when two candidates tie and the path taken when the budget runs out picks one, or when one tied
candidate has evidence. Planted tasks carry no paper, so B's evidence part rarely applies. D, E and F act more
often: on every -h case whose claims sweep a knob (D's hold), and on every task with an evaluation switch or code
leads (E, F), so they also move runs away from the settings search. Expect a handful of tasks where the arms
differ. That is too few for a sign test to reach significance unless they all go one way, and then only with 6
or more.

**Decision rule.** c7 is adopted if all four hold:
1. no confidently wrong answer and no crash in the c7 arm;
2. no more tasks worse than better;
3. every task where the arms differ is traced to a note from A or B, or to the arms' different runs;
4. the dev suite pooled over two replicates is within 5 of c5's 99.

Otherwise c5 stays.

**Result.** Seed 8 made 29 gap tasks and 14 controls (scores in `eval/planted/curriculum/scores-run-c{5,7}-s8.json`):

| | Gap tasks correct | Level 1 | Level 2 | Confidently wrong | Controls |
|---|---|---|---|---|---|
| c5 | 13 of 29 | 8 of 17 | 5 of 12 | 0 | 14 of 14 |
| c7 | 17 of 29 | 11 of 17 | 6 of 12 | 0 | 14 of 14 |

c7 was better on 4 tasks and worse on none (sign test p = 0.125). By kind, the gain is in scale (c5 5 of 8, c7 8 of
8) and data (c5 3 of 8, c7 4 of 8); settings, code and reporting are unchanged. Each difference traces to the plan:
- L1-b3c-s8-4 and L2-pygcn-s8-1 (scale): c5's probe found the factor on the measured curve but had 0 runs at g(v)
  left. c7's hold (D) kept 6 and 11 runs for it, and the factor fit every swept claim.
- L1-b3c-s8-2 (scale): c5 ran out of budget in the combine round. c7's early code screen ran 3 literal-lead
  configurations on code that ran (E), and the settings search named batch_size=512.
- L1-vgae-s8-2 (data): the arms' runs differ. c7 used 130 of 150 runs, and its mutation round found the training
  cut; c5 named test_percent=60 and had no room for the mutation round.

No c7 search crashed, and every task has a report. All four conditions hold, so **c7 is adopted**. Seed 8 is dev
data from here on.

## c8, withdrawn after the dev suite; c9 without its M

c8 (`planted-c8`, 1b6bf29) is c7 plus I, J, L, M and K, all found on c7's real-paper reruns:
- **I:** no retry of a configuration that failed with no sign of the environment at fault.
- **J:** patch values for literals written `30.` or `.5`.
- **L:** a second call for a contrast difference named without the paper's number.
- **M:** a hold for the value interval's runs.
- **K:** the audit ranks code that ran.

**The dev suite failed it.** Pooled over two replicates (bases 13000 and 13100), c8 found the cause in 92 of 138
runs, against c7's 100 (12000, 12100) and c5's 99. Against c7, 1 task was better and 6 worse. There were no
confident mistakes, and all 114 abstentions were correct. 92 is more than five below c5's 99, the bar set above for
c7, and c8 is not adopted.

**An ablation on the eight tasks that moved** (3 runs each, one replicate per arm; the tasks were picked because
c8 did worse on them, so all arms regress toward their mean):

| Arm | Correct of 24 |
|---|---|
| c7 | 16 and 19 (its two replicates) |
| c8 | 10 and 16 |
| c8 without M | 19 |
| c8 without I | 14 |

The loss sits with M. Holding six runs for the value interval through the whole search took the confirmation runs
that break ties between values (`max_steps` 1000 or 400 for the true 500). M is withdrawn.

**c9 is c8 without M**, plus the report fix for scale answers: a scale answer now carries its own reversal and
evidence rows, not the replaced settings answer's. It is judged on the dev suite (two replicates) and then on a
fresh planted batch.

**c9's dev suite** (`planted-c9`, f90b212; bases 15000 and 15100): 96 of 138, against c7's 100 and c5's 99. Against
c7, 2 tasks were better and 4 worse (sign test p = 0.69). There were no confident mistakes, and all 114 abstentions
were correct. 96 is within 5 of c5's 99, so c9 passes the no-harm check. It had no planted batch of its own: its
real-paper reruns found two more defects first (next section), so the fresh batch judges c10.

## c10: two holds and a repeat (N, O, P)

c9's reruns of RippleNet and BOND (`demo/runs/real-c9`, `real-c8`) ended unexplained with budget unspent:
- **N.** The runs held for the patch round after the combine round were released only under `code_hold`, which
  is off by default (c2 was not adopted). So a hold, once set, kept its runs from every later stage: the
  mutation round, the protocol tests and any later claim. It is now released when the patch round is done.
- **O.** The hold was the whole patch share (15% of the budget), even when the early code screen had already run
  every configuration the round would screen. It now covers only the round's configurations without a run, plus
  one fit's confirmation and counterfactual repeats. When the contrast step will name leads later (a model
  reading of the paper), the round's configurations are unknown, and the whole share is still held.
- **P.** History matching names no fit that has a single run, and nothing gave one a second. Before it labels an
  unexplained claim, it now runs the target's two closest fits a second time when the budget allows.

On RippleNet c9, a 30-run hold blocked the bisection of the repo's declared block (lr 1e-3, L2 1e-5, its closest
fit). The patch round then needed none of those runs, and the mutation round stopped at 170 of 200. On BOND c8, the
closest fit (the balance weight at 0.95) had one run, with 13 of 60 runs left. These two papers revealed N, O and P,
so they are not evidence for c10. Each fix has a toy that fails on c9 (`tests/integration/test_c10_toys.py`).

**Plan for seed 9, written before the batch was made.** c10 (`planted-c10`) is c7 plus I, J, L, K (c8 without M),
the scale-answer report fix (c9), and N, O, P. Seed 9 has the size of seeds 7 and 8: 4 tasks per case and level
on the hand harnesses, 2 on the -h ones. It is searched by c7 as adopted and by c10, both with the proposer off.
The dev suite is run twice on c10 (bases 16000 and 16100) against c7's 12000 and 12100.

On the planted batch, I, O and N act when a task is out of space with literal leads (code and data tasks mostly),
P when the claims are out of space (suspected) with the target's closest fit run once, and I on a failed run. J, L
and K act only with a paper or on literals written `30.`, which the planted cases rarely have. Expect few tasks
where the arms differ.

**Decision rule**, as for seed 8. c10 is adopted if all four hold:
1. no confidently wrong answer and no crash in the c10 arm;
2. no more tasks worse than better;
3. every task where the arms differ is traced to a note from one of c10's changes, or to the arms' different runs;
4. the dev suite pooled over two replicates is within 5 of c7's 100.

Otherwise c7 stays.

**c10's dev suite** (bases 16000 and 16100): 100 of 138, the same as c7's 100. Against c7, 4 tasks were better
and 4 worse, each by one run of six. There were no confident mistakes, and all 114 abstentions were correct.
Condition 4 holds.

## Infrastructure notes

- The machine lost DNS for minutes at a time. Task making waits for the network and doesn't count draws lost to
  it, and searches resume from `run.cut*` through `--resume`.
- A new worktree needs `.env` copied in, because the file is git-ignored.
- All Sandboxes runs were unbilled. The searches' only model calls were the name-matching step (15 Super calls, under $0.01, on seed 4).
